# BLO App Explorer

A local, browser-based explorer for the `in.gov.eci.bloapp` (BLO App) release history,
built entirely from the decompiled/extracted data in this repo — no login or live
API access required.

## Run it

```
cd explorer
python3 -m http.server 8000
```

Then open http://localhost:8000 in a browser. (It must be served over HTTP, not
opened as a `file://` path — the browser blocks `fetch()` for local files.)

## What's in it

- **Timeline** — all 30 releases (v9.39 &rarr; v9.68), with per-version diffs of
  screens, UI strings, services, receivers and permissions.
- **Screens & Features** — every activity ever seen across the 30 releases, grouped
  into modules, with a presence timeline showing when each one existed.
- **Flow Explorer** — a navigation graph (screens/fragments + `startActivity` /
  fragment-transaction edges) for v9.39 (baseline) and v9.68 (latest), extracted
  from the full decompiled Java source. Drag nodes, filter by module, click a node
  to see what it navigates to/from.
- **Try the App** — a clickable, fillable mock of the actual app UI: real screens
  rebuilt from the decompiled v9.68 layout XML, with real field labels, hints,
  required-field markers and radio/checkbox choices (all @string references
  resolved to their real text). No login, no backend, nothing you type is sent
  anywhere. Buttons are wired to real navigation targets where we can confidently
  match them; every screen also shows a **Reached from** / **Navigates to** linkage
  panel (who links here, where it links to — built from the same v9.68 call graph
  as Flow Explorer) so you can always keep exploring. Every screen also shows its
  real **network calls** (HTTP verb + path, extracted from the app's own Retrofit
  interfaces — 344 endpoints indexed across `RestClient`, `UserClient`,
  `ApiInterface`), whether it hands data back via `setResult(...)` (**returns to
  caller**), and if it runs through a verified on-device SDK with no network calls
  of its own (**runs entirely on-device**) — e.g. the face-capture screen shows it
  makes no network call and returns `file_uri`, while the screen that launched it
  shows the `POST face-detection/check-face` call it makes with that file. All of
  this is derived generically for all 191 mapped screens, not hand-annotated per
  screen.
- **Embedded SDKs** — an inventory of every third-party library bundled in v9.68
  beyond the app's own code: class counts, bundled native libraries (`.so`) and
  model assets (`.tflite`/`.emd`/`.pb`), which app files reference each one, and a
  network-code signal. Only Yoti Face Capture has been traced end-to-end and is
  marked verified; everything else shows raw evidence with an explicit caveat
  rather than an unverified verdict.
- **Compare Versions** — pick any two releases and get the full accumulated diff
  between them (not just consecutive-version deltas).
- **Search** — full-text search across screen names and UI string keys/text, with
  the version range each one was present in.

## Regenerating the data

All data under `data/` is generated by two scripts:

```
cd ..
python3 scripts/build_explorer_data.py   # timeline/features/search/flow graphs
python3 scripts/build_ui_mock_data.py    # "Try the App" screen reconstructions
python3 scripts/build_sdk_inventory.py   # "Embedded SDKs" inventory
```

`build_explorer_data.py` reads `extracted/<version>/{AndroidManifest.xml,strings.xml}`
(all 30 versions) and `decompiled/{9.39,9.68}_src/sources` (flow graphs only).
`build_ui_mock_data.py` reads `decompiled/9.68_src/sources` (to map each
Activity/Fragment to its layout via ViewBinding/`setContentView`/`inflate` calls),
`decompiled/9.68_res/.../res/layout/*.xml` (to parse the actual widget tree), and
`decompiled/9.68_src/sources/in/gov/eci/bloapp/api/{RestClient,service/UserClient}.java`
+ `network/ApiInterface.java` (to index Retrofit endpoints for the network-call
section). `build_sdk_inventory.py` reads the same decompiled source tree plus the
raw `apks/BLOApp_9.68.xapk` (for native `.so` sizes and bundled model assets).
Re-run all three after adding a new version's extracted/decompiled output.

## Notes / limitations

- Flow graphs only exist for v9.39 and v9.68 (the two fully-decompiled versions).
  Building them for all 30 would require decompiling full Java source for every
  release — see the script's `FLOW_VERSIONS` list if you want to extend this.
- The flow graph only captures navigation expressed as `new Intent(ctx, X.class)`
  and `FragmentTransaction.replace/add(id, new XFragment())` calls found via
  static regex over decompiled source — obfuscated/reflective navigation and
  WebView-driven flows aren't captured.
- "Features" are inferred from Java package structure + class name, not from an
  authoritative feature list, since the app ships no changelog of its own.
- "Try the App" only covers v9.68 (191 of 154 activities + fragments mapped — some
  screens' layouts can't be resolved statically, e.g. custom views or layouts
  picked at runtime); those show a "no layout could be reconstructed" placeholder
  but still list their real reachable screens. Dropdowns show real field labels
  but not real option lists (those are fetched from the server at runtime).
  Buttons are matched to navigation targets by label similarity — when a screen
  has several unlabeled/ambiguous actions, some links surface in the "Also
  reachable from here" panel instead of directly on the button.
- Network-call extraction only runs on screens that visibly instantiate one of
  the app's own Retrofit interfaces (`.create(RestClient.class)` etc.) — this
  gate exists because common getter names (`getState()`, `getName()`, ...)
  collide with unrelated Retrofit method names otherwise, producing false
  positives. A screen that makes calls through a shared helper method defined
  in another class (rather than inline) won't show them.
- The "runs entirely on-device" badge only appears for libraries in
  `VERIFIED_ON_DEVICE_SDKS` (`build_ui_mock_data.py`) — currently just Yoti Face
  Capture. Adding an entry there means we've actually traced it (no network code
  in the library + the calling screen never touches a Retrofit client), not just
  guessed from a quick scan. Everything else in the Embedded SDKs tab shows raw
  signal (class counts, http-literal hits) with an explicit "not verified" caveat
  instead of a claim either way.
- Screen-to-screen linkage (Reached from / Navigates to) is read from the same
  v9.68 flow graph as Flow Explorer, so it has the same coverage limits: only
  `startActivity`/fragment-transaction calls found via static regex, and only for
  the 95 nodes in that graph. A mapped screen absent from the graph shows "no
  known screen links here directly."
